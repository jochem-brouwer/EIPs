## Abstract

Adds a new transaction whose validity and gas payment can be defined abstractly. This is achieved by decomposing the transaction into a sequence of *frames* which are contract calls that validate the transaction, approve gas payment, and execute standard user operations.

## Motivation

The frame transaction type offers UX and security benefits across many areas:

- it provides a native off-ramp from the elliptic curve based cryptographic system used to authenticate transactions today, to post-quantum (PQ) secure systems.
- accounts are unlinked from their ECDSA keys, allowing native key rotation
- smart accounts become simpler and therefore safer by natively providing batch call processing
- alternative fee payment schemes are supported without centralized, third party relayers
- the default account gives the protocol an even stronger guarantee on the lowest common denominator of account functionality
 
Ultimately, frame transactions realize the original vision of account abstraction: an account simply becomes an address with code. It leverages the EVM to support arbitrary *user-defined* definitions of validation and gas payment.

## Specification

### Constants

| Name                          | Value             |
|-------------------------------|-------------------|
| `FRAME_TX_TYPE`               | `0x06`            |
| `FRAME_TX_INTRINSIC_COST`     | `15000`           |
| `FRAME_TX_PER_FRAME_COST`     | `475`             |
| `ENTRY_POINT`                 | `address(0xaa)`   |
| `MAX_FRAMES`                  | `64`              |

This EIP defines no system contracts. Replay protection, deadline checks, signature schemes, paymasters, batching, and similar features are implemented entirely in EVM as user-deployed contract code (with one signature_carrier elision pattern recognized for the `compute_sig_hash` rule — see [Signature Hash](#signature-hash)). EOAs without delegated code are served by a small protocol-provided default-code behavior (see [Default code](#default-code)).

### Frame Transaction

A new [EIP-2718](./eip-2718.md) transaction with type `FRAME_TX_TYPE` is introduced. Transactions of this type are referred to as **frame transactions**.

#### Payload Encoding

The payload is defined as the RLP serialization of the following:

```
[chain_id, sender, frames, max_priority_fee_per_gas, max_fee_per_gas, max_fee_per_blob_gas, blob_versioned_hashes]

frames = [[mode, flags, target, gas_limit, value, data], ...]
```

Replay protection is no longer part of the outer envelope. A frame transaction is replay-protected by its verifier frame, which either (a) bumps `state[tx.sender].nonce` via default code (EOAs), or (b) maintains its own replay-protection state in `tx.sender`'s storage (smart accounts, including EIP-7702-delegated EOAs). See [Replay protection](#replay-protection) under Behavior, and [Mempool](#mempool) for the public-mempool acceptance rules.

#### Field Definitions

Below are high-level definitions of each field in the transaction definition. Detailed behavior is defined in subsequent sections.

##### Outer transaction payload

- `chain_id` -- the chain ID in which the transaction is valid.
- `nonce` -- nonce of the sender to prevent replays.
- `sender` -- the address of the intended sender of the transaction.
- `frames` -- list of frames to execute.
- `max_priority_fee_per_gas` -- the EIP-1559 priority fee per gas the transaction will pay.
- `max_fee_per_gas` -- the maximum EIP-1559 fee the transaction is willing to pay, per gas.
- `max_fee_per_blob_gas` -- the maximum EIP-4844 fee per blob gas the transaction is willing to pay. Must be `0` if `blob_versioned_hashes` is empty.
- `blob_versioned_hashes` -- list of EIP-4844 blob versioned hashes.

##### Frame object

- `mode` -- the mode specifies the specific execution semantics the frame will execute with.
- `flags` -- specifies optional frame / mode features.
- `target` -- the destination or `to` address for the frame.
- `gas_limit` -- the maximum gas allowed to be execute in pursuit of the frame.
- `value` -- the amount in wei that should transferred from the `sender` as part of the frame execution.
- `data` -- the calldata provided to the top level call frame.

The `mode` of each frame sets the context of execution. It allows the protocol to identify
the purpose of the frame within the execution loop.

| `mode`  | Name           | Summary                                    |
|---------|----------------|--------------------------------------------|
| 0       | `DEFAULT` mode | Execute frame as `ENTRY_POINT`             |
| 1       | `VERIFY` mode  | Frame identifies as transaction validation |
| 2       | `SENDER` mode  | Execute frame as `sender`                  |


The `flags` field configures additional execution constraints. Bit positions are zero-based, with the least significant bit numbered `0`.

| Flag bits | Meaning                      | Valid with  |
|-----------|------------------------------| ----------- |
| 0-1       | Approval scope               | Any mode    |
| 2         | Atomic batch                 | Any mode    |

The `Valid with` column indicates the mode under which the flag is valid. If a flag is not valid under the current mode, the transaction is invalid.

#### Constraints

Some validity constraints can be determined statically. They are outlined below:

```python
assert tx.chain_id < 2**256
assert len(tx.frames) > 0 and len(tx.frames) <= MAX_FRAMES
assert len(tx.sender) == 20

total_frame_gas = 0
for frame in tx.frames:
    assert frame.mode < 3
    assert frame.flags < 8
    assert frame.target is None or len(frame.target) == 20
    assert frame.gas_limit <= 2**64 - 1
    assert frame.value < 2**256
    assert frame.mode == SENDER or frame.value == 0
    total_frame_gas += frame.gas_limit
    assert total_frame_gas <= 2**64 - 1

    # Atomic batch flag (bit 2 of flags) requires a subsequent frame to batch with.
    if frame.flags & ATOMIC_BATCH_FLAG:
        assert i + 1 < len(tx.frames)                  # must not be last frame
```

#### Receipt Encoding

The `ReceiptPayload` is defined as:

```
[cumulative_gas_used, payer, [frame_receipt, ...]]
frame_receipt = [status, gas_used, logs]
```

`payer` is the address of the account that paid the fees for the transaction. `status` is the return code of the top-level call. A new code `0x3` is introduced for frames which are skipped due to failed atomic batch.

#### Signature Hash

With the frame transaction, the signature may be at an arbitrary location in the frame list. In the canonical signature hash, every frame with mode `VERIFY` whose target's runtime code matches a recognized **signature-carrier pattern** will have its data elided. All other `VERIFY` frame data is covered by the signature hash:

```python
def compute_sig_hash(tx: FrameTx) -> Hash:
    for i, frame in enumerate(tx.frames):
        if frame.mode == VERIFY and is_signature_carrier(frame.target):
            tx.frames[i].data = Bytes()
    return keccak(bytes([FRAME_TX_TYPE]) + rlp(tx))
```

`is_signature_carrier(target)` returns `true` if `target`'s runtime code (resolved through any EIP-7702 delegation indicator) matches a recognized signature-carrier pattern, or if `target` has empty code and `target == tx.sender` (the default-code path). This EIP recognizes the default-code path; future EIPs MAY add additional signature-carrier patterns (e.g., post-quantum signature verifiers) without modifying this EIP.

For all other targets — paymasters, contracts maintaining nonce/nullifier state, expiry checkers, batchers, anything else — the `VERIFY` frame `data` is committed by the signature hash. Anything the sender authors and wants protected from in-flight mutation is committed by default; only frames whose `data` *is* the signature over `compute_sig_hash(tx)` are elided.

### Replay Protection

The execution layer does not enforce a single replay-protection scheme. Replay protection is the responsibility of the verifier code that runs in the validation prefix:

- For EOAs whose code is empty (no EIP-7702 delegation), the protocol-provided [default code](#default-code) increments `state[tx.sender].nonce` as part of every successful payment-approval transition. The sender's signature commits to the pre-state nonce, preventing replay.
- For accounts whose code is non-empty (including EOAs with an EIP-7702 delegation indicator), replay protection is provided by the account's own code, which MUST modify `tx.sender`'s storage as part of validation to make the same transaction non-repeatable. Typical implementations maintain a `mapping(uint256 => uint64)` of keyed nonces (or a `mapping(bytes32 => bool)` of consumed nullifiers) keyed by application-defined criteria; see [Examples](#examples).

The protocol provides exactly one primitive to make this work: a `VERIFY` frame's `resolved_target` may `SSTORE` to its own storage during execution, and those writes are journaled as approval effects (see [Approval effects](#approval-effects)). Without this primitive, contracts could not record replay-protection state during validation because `VERIFY` is otherwise `STATICCALL`-like.

The public mempool restricts which validation-prefix shapes it propagates so that nodes can pattern-match on default-code behavior or on recognized verifier templates and avoid relying on arbitrary contracts to do replay protection correctly. See [Mempool](#mempool).

#### Behavior

When processing a frame transaction, perform the following steps.

To begin processing a frame transaction:

1. Initialize transaction-scoped variables:
    - `payer = None`
    - `sender_approved = false`
1. Let `resolved_target = frame.target if frame.target is not None else tx.sender`
    - Unless otherwise stated, checks that refer to the target account during execution use the resolved target.

Replay protection is the responsibility of the verifier code that runs in the validation prefix (see [Replay Protection](#replay-protection)). The execution layer does not enforce a single replay scheme; the public mempool's acceptance rules (see [Mempool](#mempool)) decide which schemes propagate.

Then for each frame:

1. Execute a call with the specified `mode`, `flags`, `resolved_target`, `gas_limit`, `value`, and `data`.
   - If mode is `SENDER`:
       - `sender_approved` must be `true`. If not, the transaction is invalid.
       - Set `caller` as `tx.sender`.
   - If mode is `DEFAULT` or `VERIFY`:
       - Set the `caller` to `ENTRY_POINT`.
   - In the top-level frame call, `CALLVALUE` is `frame.value`.
   - As with an ordinary `CALL`, if the caller does not have sufficient balance to transfer `frame.value`, the frame reverts.
   - If `resolved_target` code hash is empty, i.e. `0xc5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470`, execute the logic described in [default code](#default-code).
   - Otherwise, if `resolved_target` uses an [EIP-7702](./eip-7702.md) delegation indicator, execute according to [EIP-7702](./eip-7702.md)'s delegated-code semantics.
   - The `ORIGIN` opcode returns frame `caller` throughout all call depths.
   - If a frame's execution reverts, its state changes are discarded. Additionally, if this frame has the atomic batch flag set, mark all subsequent frames in the same atomic group as skipped.
2. If frame has mode `VERIFY` the following additional requirements are imposed:
    - Execute the frame as a `STATICCALL`, disallowing state manipulation, with two exceptions:
      - The `APPROVE` instruction (sets `payer`/`sender_approved` as approval effects).
      - `SSTORE` to `resolved_target`'s own storage (i.e., writes the frame's own contract code performs against its own slots, including writes performed via `DELEGATECALL` from `resolved_target`). These writes are journaled as approval effects.
    - If the frame reverts, the transaction is invalid.
3. If a frame is part of an atomic batch and it fails, unroll the associated atomic batch.
    - An **atomic batch** is a maximal contiguous sequence of frames `[i, j]` where `j > i`, frames `i` through `j - 1` have `ATOMIC_BATCH_FLAG` set, and frame `j` does not have `ATOMIC_BATCH_FLAG` set.
    - When a frame in the batch fails, the state must be rolled back to the condition it was immediately before the atomic batch began. All remaining frames in the atomic batch are skipped.
    - Since skipped frames are not executed, the gas value allotted to them is refunded at the end of the transaction.
    - If the frame does not have an associated atomic batch, further special
      handling is not needed, simple revert the individual frame.

After executing all frames, verify that `payer != None`. If it is not, the transaction is invalid. If it is, refund any unpaid gas to the payer.

##### Approval effects

Two kinds of state change performed during a successfully-exiting `VERIFY` frame are **approval effects**:

1. The `APPROVE` instruction's updates to `payer` and `sender_approved`.
2. `SSTORE` operations that write to `resolved_target`'s own storage (the contract's own slots, whether the write is performed directly by the contract's code or via `DELEGATECALL` from it). The default code's account-nonce increment (see [Default code](#default-code)) is also an approval effect.

Approval effects MUST be journaled outside the current frame's revert journal and outside any later atomic-batch snapshot. If the frame reverts, its approval effects are discarded along with the rest of the frame's revert journal. If the frame exits successfully (via `RETURN`, `STOP`, or `APPROVE`), its approval effects are committed and MUST NOT be reverted by later frame reverts, by frames skipped due to atomic-batch failure, or by restoring an atomic-batch state snapshot.

`SSTORE`s performed as approval effects are priced under ordinary [EIP-2200](./eip-2200.md) `SSTORE` pricing and contribute to the frame's `gas_used`. There is no special surcharge: keyed nonces, nullifier tables, expiry counters, session-key registries, and similar replay-protection or rate-limit state are all priced naturally by SSTORE economics.

`SSTORE`s outside `resolved_target`'s own storage are NOT permitted in `VERIFY` mode; the frame reverts on such an attempt. This is the same rule as for `STATICCALL` today, lifted only for the resolved target's own slots.

##### Cross-frame interactions

A few cross-frame interactions to note:

- For the purposes of gas accounting of warm / cold state status, the journal of such touches is shared across frames.
- Discard the `TSTORE` and `TLOAD` transient storage between frames.

##### Gas Accounting

The total gas limit of the transaction is:

```
tx_gas_limit = FRAME_TX_INTRINSIC_COST + len(tx.frames) * FRAME_TX_PER_FRAME_COST + calldata_cost(rlp(tx.frames)) + sum(frame.gas_limit for all frames)
```

Where `calldata_cost` is calculated per standard [EIP-7623](./eip-7623.md) rules.

The total fee is defined as:

```
tx_fee = tx_gas_limit * effective_gas_price + blob_fees
blob_fees = len(blob_versioned_hashes) * GAS_PER_BLOB * blob_base_fee
```

The `effective_gas_price` is calculated per [EIP-1559](./eip-1559.md) and `blob_fees` is calculated as per [EIP-4844](./eip-4844.md).

Any `frame.value` transferred by `SENDER` frames is separate from `tx_fee` and follows ordinary `CALL` value-transfer semantics. The gas cost of sending `frame.value` is the same as for any `CALL` instruction.

Each frame has its own `gas_limit` allocation. Unused gas from a frame is **not** available to subsequent frames. After all frames execute, the gas refund is calculated as:

```
refund = sum(frame.gas_limit for all frames) - total_gas_used
```

This refund is returned to the gas payer (the `resolved_target` that called `APPROVE(APPROVE_PAYMENT)` or `APPROVE(APPROVE_EXECUTION_AND_PAYMENT)`) and added back to the block gas pool.

##### Default code

Frame transactions can be used by accounts who do not have deployed code, nor an [EIP-7702](./eip-7702.md) delegation indicator via the "default code" mechanism. Default code provides the canonical ECDSA signature-carrier behavior in-band, so an EOA can act as its own verifier without first deploying code. Conceptually, an empty-code account behaves as if delegated to the canonical ECDSA verifier (see [Canonical ECDSAVerifier](#canonical-ecdsaverifier-default-code)).

EOAs without a contract or delegation indicator have no storage of their own; replay protection for them is provided by the protocol via `state[tx.sender].nonce`, which the default code reads, commits to via signature, and increments as an approval effect.

The behavior of the default code is:

- If `mode` is `VERIFY`:
  - Read the allowed approval scope from the flags field: `allowed_scope = frame.flags & APPROVE_SCOPE_MASK`. If `allowed_scope == APPROVE_SCOPE_NONE`, revert.
  - If `allowed_scope & APPROVE_EXECUTION != 0` and `resolved_target != tx.sender`, revert.
  - Read the first byte of `frame.data` as `signature_type`.
  - If `signature_type` is:
    - `0x0`:
      - Read the rest of `frame.data` as `(v, r, s)`.
      - If `s > secp256k1n / 2`, revert.
      - Let `sig_hash = keccak256(compute_sig_hash(tx) || uint64_be(state[tx.sender].nonce))`. The pre-state account nonce is committed by the signature, preventing replay.
      - Let `recovered = ecrecover(sig_hash, v, r, s)`.
      - If `recovered == address(0)` or `resolved_target != recovered`, revert.
    - Otherwise revert.
  - Increment `state[tx.sender].nonce` as an approval effect.
  - Call `APPROVE(allowed_scope)`.
- If `mode` is `SENDER` or `DEFAULT`:
  - Return successfully as if calling empty code.

The default code is the only signature-carrier pattern this EIP recognizes. Future signature schemes (e.g., post-quantum verifiers, BLS aggregation) MAY be introduced as additional recognized signature-carrier patterns or as ordinary contract code that accounts opt into via [EIP-7702](./eip-7702.md) delegation indicators; in either case, no change to this EIP is required.

### `APPROVE` Instruction (`0xaa`)

The `APPROVE` instruction exits the current EVM call frame successfully and updates the transaction-scoped approval context based on the `scope` operand.

#### Stack

| Stack      | Value        |
| ---------- | ------------ |
| `top - 0`  | `offset`     |
| `top - 1`  | `length`     |
| `top - 2`  | `scope`      |

#### Scope Operand

The `scope` operand is a bitmask. Define the following constants:

- `APPROVE_NONE` (`0x0`): No approval scope allowed - the current frame is not allowed to approve any scope.
- `APPROVE_PAYMENT` (`0x1`): Approval of payment - the contract approves paying the total gas cost for the transaction.
- `APPROVE_EXECUTION` (`0x2`): Approval of execution - the sender contract approves future frames calling on its behalf.
   - Note this is only valid when `resolved_target` equals `tx.sender`.
- `APPROVE_EXECUTION_AND_PAYMENT` (`0x3`): Approval of payment and execution.

`APPROVE_SCOPE_MASK` is defined as an alias for `APPROVE_EXECUTION_AND_PAYMENT`.

### Introspection

The instructions in this section provide the needed introspection capabilities of the new frame transaction type and the frame objects themselves, including some runtime information like the execution result status.

#### `TXPARAM` Instruction `(0xb0)`

This instruction gives access to transaction-scoped information. The gas cost of this operation is `2`. It takes one value from the stack, `param`, and returns the associated transaction value to the stack. See the table for the full mapping.

| `param` | Return value                                                                |
|---------|-----------------------------------------------------------------------------|
| 0x00    | current transaction type                                                    |
| 0x02    | `sender`                                                                    |
| 0x03    | `max_priority_fee_per_gas`                                                  |
| 0x04    | `max_fee_per_gas`                                                           |
| 0x05    | `max_fee_per_blob_gas`                                                      |
| 0x06    | max cost (basefee=max, all gas used, includes blob cost, and intrinsic cost) |
| 0x07    | `len(blob_versioned_hashes)`                                                |
| 0x08    | `compute_sig_hash(tx)`                                                      |
| 0x09    | `len(frames)`                                                               |
| 0x0A    | currently executing frame index                                             |

`param = 0x01` is reserved and reverts on lookup; it formerly returned an outer-envelope `nonce` field, which no longer exists. Replay-protection state is now contract-managed; verifier code reads it directly from `SLOAD` against `tx.sender`'s own storage rather than via `TXPARAM`.

Smart accounts that need to commit to a sequence number or nullifier in their signature scheme should derive `sig_hash = keccak256(TXPARAM(0x08) || application_state)` where `application_state` is whatever the contract chooses (a keyed-nonce sequence, a nullifier, a session-key index, etc.). The protocol does not prescribe this derivation.

Undefined `param` values result in an exceptional halt.

#### `FRAMEDATALOAD` Instruction `0xb1`

This opcode loads one 32-byte word of data from frame input. Gas cost: 3 (matches CALLDATALOAD).

It takes two values from the stack, an `offset` and `frameIndex`.
It places the retrieved data on the stack.

When the `frameIndex` is out-of-bounds, an exceptional halt occurs.

The operation semantics match CALLDATALOAD, returning a word of data from the chosen
frame's `data`, starting at the given byte `offset`. When targeting a frame in `VERIFY`
mode, the returned data is always zero.

#### `FRAMEDATACOPY` Instruction (`0xb2`)

This opcode copies data frame input into the contract's memory. Its gas cost is calculated
exactly as for `CALLDATACOPY`, including the fixed cost of 3, the per-word copy cost, and
the standard EVM memory expansion cost.

It takes four values from the stack: `memOffset`, `dataOffset`, `length` and `frameIndex`.
No stack output value is produced.

When the `frameIndex` is out-of-bounds, an exceptional halt occurs.

The operation semantics match CALLDATACOPY, copying `length` bytes from the chosen frame's
`data`, starting at the given byte `dataOffset`, into a memory region starting at
`memOffset`. When targeting a frame in `VERIFY` mode, no data is copied.

#### `FRAMEPARAM` Instruction (`0xb3`)

This instruction gives access to frame-scoped information. The gas cost of this operation is `2`. It takes two values from the stack, `frameIndex` on top and `param` second from top.

| `param` | `frameIndex` | Return value                                              |
|---------|--------------|-----------------------------------------------------------|
| 0x00    | frameIndex   | `resolved_target`                                         |
| 0x01    | frameIndex   | `gas_limit`                                               |
| 0x02    | frameIndex   | `mode`                                                    |
| 0x03    | frameIndex   | `flags`                                                   |
| 0x04    | frameIndex   | `len(data)`                                               |
| 0x05    | frameIndex   | `status` (exceptional halt if current/future)             |
| 0x06    | frameIndex   | `allowed_scope` (`frame.flags & APPROVE_SCOPE_MASK`)      |
| 0x07    | frameIndex   | `atomic_batch` (`(frame.flags >> 2) & 0x01`, returns 0/1) |
| 0x08    | frameIndex   | `value`                                                   |

Notes:

- The `status` field (0x05) returns `0` for failure or `1` for success.
- Undefined `param` values result in an exceptional halt.
- Out-of-bounds access for `frameIndex` results in an exceptional halt.
- Attempting to access the return `status` of the current frame or a subsequent frame results in an exceptional halt.
- `len(data)` returns size 0 when called on a frame with `VERIFY` set.

### Mempool

The transaction mempool must carefully handle frame transactions, as a naive implementation could introduce denial-of-service vulnerabilities. The fundamental goal of the public mempool rules is to avoid allowing an arbitrary number of transactions to be invalidated by a single environmental change or state modification. Beyond this, the rules also aim to minimize the amount of work needed to complete the initial validation phase of a transaction before an acceptance decision can be made.

This policy is inspired by [ERC-7562](./eip-7562.md), but removes staking and reputation entirely. Any behavior that ERC-7562 would admit only for a staked or reputable third party is rejected here for the public mempool. Transactions outside these rules may be accepted into a local or private mempool, but must not be propagated through the public mempool.

#### Constants

| Name  | Value  | Description  |
|---|---|---|
| `MAX_VERIFY_GAS`   | `100_000`  | Maximum amount of gas a node should expend simulating the validation prefix |
| `MAX_PENDING_TXS_USING_NON_CANONICAL_PAYMASTER`   | `1`  | Maximum amount of pending transactions that can be using any given non-canonical paymaster |

#### Validation Prefix

The **validation prefix** of a frame transaction is the shortest prefix of frames whose successful execution sets `payer != None`.

Public mempool rules apply only to the validation prefix. Once `payer` is set, subsequent frames are outside public mempool validation and may be arbitrary. In particular, `user_op` and `post_op` occur after payment approval and are therefore not subject to the public mempool restrictions below.

#### Policy Summary

A frame transaction is eligible for public mempool propagation only if its validation prefix depends exclusively on:

1. transaction fields, including the canonical signature hash,
2. `state[tx.sender]` — its code, storage slots read during validation, and (for the default-code path) account nonce,
3. the block timestamp, as read by an [expiry frame](#expiry-frame),
4. if a deploy frame is present, the code of the factory targeted by that frame (subject to the deploy-frame trace rules below),
5. if a paymaster frame is present, either a canonical paymaster instance together with explicit paymaster balance reservation, or a non-canonical paymaster being used by less than `MAX_PENDING_TXS_USING_NON_CANONICAL_PAYMASTER` pending transactions,
6. the code of any other existing non-delegated contracts reached during validation via `CALL*` or `EXTCODE*`, provided the resulting trace does not access disallowed mutable state.

Any dependency on third-party mutable state outside these categories must result in rejection by the public mempool.

A transaction whose frame layout does not match a recognized validation prefix (see below) is rejected by the public mempool. Builders MAY include unmatched transactions via private or out-of-band paths.

##### Replay Protection in the Public Mempool

The execution layer does not enforce replay protection (see [Replay Protection](#replay-protection)). The public mempool MUST nevertheless propagate only transactions whose validation prefix is replay-protected. A validation prefix is considered replay-protected if **at least one** of the following holds:

1. The verifier frame's `resolved_target` has empty code, in which case the protocol-provided [default code](#default-code) increments `state[tx.sender].nonce` as an approval effect.
2. The verifier frame's `resolved_target` resolves (through any EIP-7702 delegation indicator) to runtime code that the node recognizes as a **safe verifier template** known to record per-transaction replay-protection state in `tx.sender`'s own storage. The set of recognized templates is a versioned mempool policy external to this EIP; nodes MAY refuse to propagate transactions whose verifier code they do not recognize.

Conditions (1) and (2) are mutually exclusive in practice: (1) applies to vanilla EOAs, (2) to smart accounts and EIP-7702-delegated EOAs.

#### Frame Role Subclassifications

While the frames are designed to be generic, the mempool recognizes specific frame *roles*. Roles are how the mempool reasons about a frame's purpose without baking that purpose into the consensus layer.

- `expiry_verify` (VERIFY): recognized by `frame.target`'s runtime code matching the canonical `ExpiryVerifier` pattern (see [Expiry Frame](#expiry-frame)). Deadline check; eligible for the `TIMESTAMP` exception.
- `self_verify` (VERIFY): `resolved_target == tx.sender` and calls `APPROVE(APPROVE_EXECUTION_AND_PAYMENT)`. Validates the transaction and approves both sender and payer. Must be replay-protected per [Replay Protection in the Public Mempool](#replay-protection-in-the-public-mempool).
- `only_verify` (VERIFY): `resolved_target == tx.sender` and calls `APPROVE(APPROVE_EXECUTION)`. Validates the transaction and approves only the sender. Must be replay-protected.
- `pay` (VERIFY): calls `APPROVE(APPROVE_PAYMENT)` (a canonical paymaster instance is eligible by code match). Validates and approves payment.
- `deploy` (DEFAULT): typically targets a deterministic factory such as the [EIP-7997](./eip-7997.md) predeploy. Deploys a new smart account at `tx.sender`.
- `user_op` (SENDER): executes the intended user operation.
- `post_op` (DEFAULT): optional post-op action invoked by the paymaster.

The public mempool recognizes four validation prefix shapes. An `expiry_verify` frame MAY appear at any position in the frame list; for the purpose of pattern matching it is skipped.

##### Canonical Paymaster

###### Basic Transaction

```
+-------------+-----+
| only_verify | pay |
+-------------+-----+
```

###### Deploy New Account

```
+--------+-------------+-----+
| deploy | only_verify | pay |
+--------+-------------+-----+
```

Frames after these prefixes are outside public mempool validation. A transaction may continue with any number of `user_op`s and/or `post_op`s.

The set of recognized validation prefixes is a versioned policy external to this EIP. Adding a new prefix (for example, to introduce a post-quantum signature-carrier flow, or a different paymaster shape) does not require revisiting the execution-layer specification.

#### Structural Rules

To be accepted into the public mempool, a frame transaction must satisfy the following:

1. Its validation prefix must match one of the four recognized prefixes above (with `expiry_verify` frames skipped for pattern-matching purposes).
2. If present, `deploy` must be the first frame. This implies there can be at most one `deploy` frame in the validation prefix.
3. The verifier frame (`self_verify` or `only_verify`) MUST be replay-protected per [Replay Protection in the Public Mempool](#replay-protection-in-the-public-mempool).
4. `self_verify` and `only_verify` MUST execute in `VERIFY` mode, target `tx.sender` (either explicitly or via a null target), and successfully call `APPROVE`.
    - `self_verify` MUST call `APPROVE(APPROVE_EXECUTION_AND_PAYMENT)`.
    - `only_verify` MUST call `APPROVE(APPROVE_EXECUTION)`.
5. `pay` MUST execute in `VERIFY` mode and successfully call `APPROVE(APPROVE_PAYMENT)`.
6. No frame in the validation prefix may have the `ATOMIC_BATCH_FLAG` set.
7. The sum of `gas_limit` values across the validation prefix must not exceed `MAX_VERIFY_GAS`.
8. Nodes should stop simulation immediately once `payer != None`.

A node SHOULD keep at most one pending frame transaction per `tx.sender` in the public mempool by default. Where a verifier template is known to support keyed-domain concurrency in sender storage (e.g., the verifier maintains a `mapping(uint256 => uint64)` of keyed nonces and the transaction commits to a specific key), nodes MAY admit concurrent pending transactions for the same sender on distinct keys, subject to template-defined dependency tracking. The mechanism is a mempool concern; this EIP does not specify it.

#### Expiry Frame

An **expiry frame** is a `VERIFY` frame whose target's runtime code matches the canonical `ExpiryVerifier` pattern below. There is no fixed address: any contract whose code matches is recognized.

The canonical `ExpiryVerifier` runtime code (8-byte big-endian deadline calldata, `STOP` if `block.timestamp <= deadline`, otherwise `REVERT`):

```text
0x60083614600a575f5ffd5b5f3560c01c4211601657005b5f5ffd
```

Equivalent behavior:

```python
if len(evm.calldata) != 8:
    revert()
expiry_timestamp = int.from_bytes(evm.calldata, "big")
if evm.timestamp > expiry_timestamp:
    revert()
stop()
```

An expiry frame is invalid unless `frame.flags == 0`, `frame.value == 0`, and `len(frame.data) == 8`. A transaction MAY contain at most one expiry frame; for the purpose of validation-prefix pattern matching, expiry frames are skipped (e.g., `[expiry_verify, self_verify]` is recognized as `[self_verify]`).

A node MUST drop a frame transaction from the public mempool if it contains an expiry frame whose deadline is less than the node's view of the current block timestamp at any point.

Expiry frames are not subject to the validation trace rules below, storage-dependency tracking, or `MAX_VERIFY_GAS`. The `TIMESTAMP` opcode is permitted only inside a frame whose executing contract's runtime code matches the canonical `ExpiryVerifier` pattern; clients may optimize the frame by performing the same deadline check without explicit EVM execution.

Anyone may deploy an `ExpiryVerifier` instance. Recognition is by runtime-code match alone, exactly like the canonical paymaster (see [Canonical Paymaster Exception](#canonical-paymaster-exception)).

#### Canonical Paymaster Exception

The generic validation trace and opcode rules below apply to all frames in the validation prefix except a `pay` frame whose target runtime code exactly matches the canonical paymaster implementation. The canonical paymaster implementation is explicitly designed to be safe for public mempool use and is therefore admitted by code match, successful `APPROVE(APPROVE_PAYMENT)`, and the paymaster accounting rules in this section, rather than by requiring it to satisfy each generic validation rule individually.

#### Validation Trace Rules

A public mempool node must simulate the validation prefix and reject the transaction if any of the following occurs before `payer` has been set:

- a frame in the validation prefix reverts
- a `self_verify`, `only_verify`, or `pay` frame exits without its required `APPROVE`
- execution exceeds `MAX_VERIFY_GAS`
- execution uses a banned opcode
- execution performs a state write, except inside the first `deploy` frame for (a) `CREATE`, `CREATE2`, or `SETDELEGATE` operations that install code at `tx.sender`, or (b) `SSTORE`s to `tx.sender`'s storage
- execution reads storage outside `tx.sender`
- execution performs `CALL*` or `EXTCODE*` to an address that is neither an existing contract nor a precompile, or to an address that uses an EIP-7702 delegation, except for `tx.sender` default-code behavior
- if a `deploy` frame is present, its execution does not result in non-empty code being installed at `tx.sender` (either conventional contract code or an EIP-7702 delegation indicator)

##### Banned Opcodes

For `VERIFY` frames, the usual `STATICCALL` restrictions apply except for the protocol-defined effects of `APPROVE`. In addition, the following opcodes are banned during the validation prefix, with a few caveats:

- ORIGIN (0x32)
- GASPRICE (0x3A)
- BLOCKHASH (0x40)
- COINBASE (0x41)
- TIMESTAMP (0x42)
    - Except in an expiry frame whose target's runtime code matches the canonical `ExpiryVerifier` pattern.
- NUMBER (0x43)
- PREVRANDAO/DIFFICULTY (0x44)
- GASLIMIT (0x45)
- BASEFEE (0x48)
- BLOBHASH (0x49)
- BLOBBASEFEE (0x4A)
- GAS (0x5A)
    - Except when followed immediately by a `*CALL` instruction. This is the standard method of passing gas to a child call and does not create an additional public mempool dependency.
- CREATE (0xF0)
    - Except inside the first `deploy` frame.
- CREATE2 (0xF5)
    - Except inside the first `deploy` frame.
- SETDELEGATE (0xF6, [EIP-7819](./eip-7819.md))
    - Except inside the first `deploy` frame.
- INVALID (0xFE)
- SELFDESTRUCT (0xFF)
- BALANCE (0x31)
- SELFBALANCE (0x47)
- SSTORE (0x55)
- TLOAD (0x5C)
- TSTORE (0x5D)

`SLOAD` can be used only to access `tx.sender` storage, including when reached transitively via `CALL*` or `DELEGATECALL`.

`CALL*` and `EXTCODE*` may target any existing contract or precompile, provided the resulting trace still satisfies the storage, opcode, and EIP-7702 restrictions above. This permits helper contracts and libraries during validation, including via `DELEGATECALL`, so long as they do not introduce additional mutable-state dependencies.

#### Paymasters

A paymaster can choose to sponsor a transaction's gas. Generally the relationship is one paymaster to many transaction senders, however, this is in direct conflict with the goal of not predicating the validity of many transactions on the value of one account or storage element.

We address this conflict in two ways:

1. If a paymaster sponsors gas for a large number of accounts simultaneously, it must be a safe, standardized paymaster contract. It is designed such that ether which enters it cannot leave except:
  a. in the form of payment for a transaction, or
  b. after a delay period.
2. If a paymaster sponsors gas for a small number of accounts simultaneously (no more than `MAX_PENDING_TXS_USING_NON_CANONICAL_PAYMASTER`), it may be any paymaster contract.

##### Canonical paymaster

The canonical paymaster is not a singleton deployment. Many instances may be deployed. For public mempool purposes, a paymaster instance is considered canonical if and only if the runtime code at the `pay` frame target exactly matches the canonical paymaster implementation.

The canonical paymaster in this draft authorizes with a single secp256k1 signer via `ecrecover`, does not support contract-signature schemes, and may change in later specifications, in which case a new canonical implementation version would be required.

Because the canonical paymaster implementation is explicitly standardized to be safe for public mempool use, nodes do not need to apply the generic validation trace and opcode rules to that `pay` frame. Instead, they identify it by runtime code match and apply the paymaster-specific accounting and revalidation rules in this section.

A transaction using a paymaster is eligible for public mempool propagation only if the `pay` frame targets a canonical paymaster instance and the node can reserve the maximum transaction cost against that paymaster.

For public mempool purposes, each node maintains a local accounting value `reserved_pending_cost(paymaster)` and computes:

```python
available_paymaster_balance = state.balance(paymaster) - reserved_pending_cost(paymaster) - pending_withdrawal_amount(paymaster)
```

Where `pending_withdrawal_amount(paymaster)` is the currently pending delayed withdrawal amount of the canonical paymaster instance, or zero if no delayed withdrawal is pending.

A node must reject a paymaster transaction if `available_paymaster_balance` is less than the transaction's maximum cost (`TXPARAM(0x06)`).

On admission, the node increments `reserved_pending_cost(paymaster)` by the transaction's maximum cost (`TXPARAM(0x06)`). On eviction, replacement, inclusion, or reorg removal, the node decrements it accordingly.

##### Non-canonical paymaster

For non-canonical paymasters, `pending_withdrawal_amount` is not meaningful since they may not support timelocked withdrawals.  Instead, we keep the mempool safe by enforcing that each non-canonical paymaster can only be used with no more than `MAX_PENDING_TXS_USING_NON_CANONICAL_PAYMASTER` pending transactions.

Therefore we perform two checks:

- For balance, `available_paymaster_balance` must not be less than the transaction cost, where:

```python
available_paymaster_balance = state.balance(paymaster) - reserved_pending_cost(paymaster)
```

- The number of pending transactions in the mempool that uses this paymaster must be less than `MAX_PENDING_TXS_USING_NON_CANONICAL_PAYMASTER`.

[See here for rationale](#non-canonical-paymasters-in-the-mempool) for enabling non-canonical paymasters in the mempool.

#### Acceptance Algorithm

1. A transaction is received over the wire and the node decides whether to accept or reject it.
2. The node analyzes the frame structure and determines the validation prefix. If the prefix is not one of the recognized prefixes (with `expiry_verify` frames skipped for matching purposes), reject.
3. The node checks that the verifier frame satisfies [Replay Protection in the Public Mempool](#replay-protection-in-the-public-mempool). Reject if it does not.
4. The node simulates the validation prefix and enforces the structural and trace rules, except that:
    - the `expiry_verify` frame is handled per [Expiry Frame](#expiry-frame),
    - a `pay` frame whose target runtime code exactly matches the canonical paymaster implementation is handled via the canonical paymaster exception and the paymaster-specific rules below.
5. The node records the dependency set for revalidation:
    - `state[tx.sender]` slots read or written during validation,
    - `state[tx.sender].nonce` (always, since the default-code path reads/writes it; smart-account templates that don't touch it leave a no-op entry),
    - any canonical paymaster instance referenced by a `pay` frame.
6. If a canonical paymaster instance is used, the node verifies paymaster solvency using the reservation rule above.
7. The pending-transaction-per-sender cap is enforced as described in [Structural Rules](#structural-rules).
8. If all checks pass, the transaction may be accepted into the public mempool and propagated to peers.

#### Revalidation

When a new canonical block is accepted, the node removes any included frame transactions from the public mempool, updates paymaster reservations accordingly, and identifies the remaining pending transactions whose tracked dependencies were touched by the block. This includes at least:

- transactions for the same `sender`,
- transactions whose recorded sender storage slots or account nonce changed,
- transactions that reference a canonical paymaster instance whose balance, code, or delayed-withdrawal state changed.

The node then re-simulates the validation prefix of only those affected transactions against the new head and evicts any transaction that no longer satisfies the public mempool rules.

#### Transaction origination

Do not apply the restriction put in place by [EIP-3607](./eip-3607.md) to frame transactions.
Specifically, `SENDER` frames originate calls where `tx.sender` is a contract account.
Validation logic for other transaction types remains unchanged, i.e. the transaction is only valid if the sender account's code is either empty or a valid delegation indicator.

## Rationale

### Canonical signature hash

The canonical signature hash is provided in `TXPARAM` to simplify the development of smart accounts.

Computing the signature hash in EVM is complicated and expensive. While using the canonical signature hash is not mandatory, it is strongly recommended. Creating a bespoke signature requires precise commitment to the underlying transaction data. Without this, it's possible that some elements can be manipulated in-the-air while the transaction is pending and have unexpected effects. This is known as transaction malleability. Using the canonical signature hash avoids malleability of the frames other than `VERIFY`.

The `frame.data` of `VERIFY` frames is elided from the signature hash. This is done for three reasons:

1. It contains the signature so by definition it cannot be part of the signature hash.
2. In the future it may be desired to aggregate the cryptographic operations for data and compute efficiency reasons. If the data was introspectable, it would not be possible to aggregate the verify frames in the future.
3. For gas sponsoring workflows, we also recommend using a `VERIFY` frame to approve the gas payment. Here, the input data to the sponsor is intentionally left malleable so it can be added onto the transaction after the `sender` has made its signature. Notably, the raw `frame.target` field of `VERIFY` frames is covered by the signature hash, i.e. the `sender` chooses the sponsor address explicitly.

The elision is therefore narrowed to **signature-carrier targets only**: a `VERIFY` frame whose target's runtime code matches a recognized signature-carrier pattern (or, equivalently, the protocol-provided default code) has its `data` elided, since that data *is* the signature over `compute_sig_hash(tx)`. Every other `VERIFY` frame's `data` is sender-authored and committed by the signature hash.

Implementations MUST NOT treat `VERIFY` frame `data` as sender-authenticated by the canonical signature hash. Any verifier or paymaster that depends on its input data, including sponsor parameters, exchange rates, fee terms, or custom account context, MUST authenticate that data independently. Replacing or mutating `VERIFY` frame `data` does not change the canonical signature hash.

By contrast, non-`VERIFY` frame metadata, including a `SENDER` frame's `value`, remains covered by the canonical signature hash.

Verification logic MUST NOT assign policy meaning to signature encodings or adjacent `VERIFY` frame data unless that meaning is independently authenticated.

### Minimal protocol surface

The execution layer's job is to (a) commit to a transaction envelope, (b) execute frames, and (c) ensure exactly one frame designates a payer for fees. Everything else — nonces, expiry, paymasters, session keys, batching, signature schemes, rate limiting — is implementable in pure EVM and lives in user-deployed contract code or in the mempool's pattern-matching policy.

To make that division work, the protocol provides exactly two primitives:

1. The `APPROVE` instruction, which sets `payer` and `sender_approved` as **approval effects** (writes journaled outside subsequent revert journals and atomic-batch rollback).
2. A widening of the `STATICCALL`-like `VERIFY`-mode rules: a frame's `resolved_target` may `SSTORE` to its own storage, and those writes are also approval effects.

That second primitive is what makes multi-dimensional nonces, nullifier tables, session-key registries, and similar replay-protection schemes implementable entirely in contract code. The contract reads its own slot, asserts it matches the transaction's claimed value, increments it, and `APPROVE`s — exactly the logic that would otherwise need to be baked into the protocol via a system contract. SSTORE pricing handles state-growth economics naturally; no special surcharge constants are needed.

Earlier drafts of this EIP and its companion EIP-8250 carried envelope-level nonce fields and a canonical `NonceManager` system contract with protocol-writable storage. Both have been removed in favor of the single primitive above. The expiry verifier, which was previously a system contract at a hardcoded address, has likewise been demoted to a runtime-code-match pattern recognized only by the mempool — exactly like the canonical paymaster has always been recognized.

### Replay protection split: protocol vs. contract

EOAs have no storage of their own (absent an EIP-7702 delegation). To preserve baseline replay protection, the protocol-provided default code increments `state[tx.sender].nonce` as an approval effect and binds the sender's signature to the pre-state nonce via `sig_hash = keccak256(compute_sig_hash(tx) || account_nonce)`. The account nonce thus continues to serve as the sequence space for plain EOAs, and that sequence space is shared with legacy, EIP-1559, EIP-4844, and EIP-7702 transactions (each of which also increments it). Users who freely move between transaction types never see two parallel sequences.

Smart accounts — including EOAs that have activated EIP-7702 — have their own storage and provide replay protection there. The verifier code is free to implement linear nonces, keyed nonces, nullifier tables, time-windowed counters, or anything else. The mempool's job is to recognize the verifier template and admit only those whose replay protection it understands.

### EIP-7702 integration

EIP-7702 introduces a delegation indicator (`0xef0100 || address`) that any EOA can install at its own account; calls to that EOA then execute the delegated code with `ADDRESS == authority`. Combined with this EIP, EIP-7702 closes the loop on EOA account abstraction without any further changes:

- **Execution.** When a frame's `resolved_target` is an EOA with a delegation indicator, the delegated code runs, exactly as in EIP-7702's existing rules. This EIP already references those rules and does not modify them.
- **Storage for replay protection.** A delegated EOA's storage is its own. The widened `VERIFY` rule above lets the delegated verifier `SSTORE` to that storage as an approval effect. Multi-dimensional nonces, nullifiers, and other application-defined replay schemes work directly on a delegated EOA with no protocol changes.
- **Signature hash.** When the delegated code matches a recognized signature-carrier pattern, the verify frame's `data` is elided in `compute_sig_hash`. When it does not, the data is committed — the contract is responsible for its own authentication scheme. Either way, the elision rule does not special-case 7702.
- **Mempool.** A 7702-delegated EOA's verifier is exactly the kind of "verifier template the node recognizes" referenced in the mempool's replay-protection rule. Common 7702 wallet implementations (canonical templates) are recognized; bespoke ones are not propagated through the public mempool but can be included via builders.
- **What this EIP does *not* do.** Installing a delegation indicator (i.e., the `authorization_list` mechanism in EIP-7702) is a separate concern; this EIP does not add a new way to install delegations. A frame transaction MAY install a delegation indicator via a `SETDELEGATE` operation (see [EIP-7819](./eip-7819.md)) inside a `deploy` frame, but the EIP-7702 authorization-list path remains the canonical way to opt in.

The net effect: under this EIP, an EOA that has activated EIP-7702 is functionally equivalent to a smart contract account for the purposes of frame transactions. Storage works. Keyed nonces work. Session keys work. Batching works. The only protocol-mandated behavior left is the default-code fallback for EOAs that have *not* activated EIP-7702.

### `APPROVE` calling convention

Originally `APPROVE` was meant to extend the space of return statuses from 0 and 1 today to 0 to 4. However, this would mean smart accounts deployed today would not be able to modify their contract code to return with a different value at the top level. For this reason, we've chosen behavior above: `APPROVE` terminates the executing frame successfully like `RETURN`, but it actually updates the transaction scoped values `sender_approved` and `payer` during execution. It is still required that only the sender can toggle the `sender_approved` to `true`. Only the frame's resolved target can call `APPROVE` generally, because it can allow the transaction pool and other frames to better reason about `VERIFY` mode frames.

Because `DELEGATECALL` preserves `ADDRESS`, code executed via `DELEGATECALL` from the resolved target may also execute `APPROVE` successfully. Contracts that rely on `APPROVE` should therefore treat delegatecalled libraries as fully trusted.

### Payer in receipt

The payer cannot be determined statically from a frame transaction and is relevant to users. The only way to provide this information safely and efficiently over the JSON-RPC is to record this data in the receipt object.

### Why blobs stay in the envelope

EIP-4844 blob commitments (`max_fee_per_blob_gas`, `blob_versioned_hashes`) remain in the outer transaction envelope rather than being expressed as a frame. The reason is that blobs are not an EVM concern; they are a consensus-layer and data-availability concern, and their existence affects block construction before any frame executes:

1. **Block propagation** needs to know up-front how many blobs are attached to each transaction, so that the blob sidecar can travel with the block.
2. **Blob-gas fee market** is a separate pool from execution gas and must be metered at block-inclusion time, before the EVM runs.
3. **KZG verification** of blob commitments happens at the consensus layer, not in the EVM.
4. **Blob expiration / garbage collection** is coordinated between the execution layer and consensus layer on a separate schedule from EVM state.

None of these are reachable from EVM bytecode, so moving the blob commitments into a frame would force the protocol to inspect the EVM-level frame structure before EVM execution — an inversion that buys nothing. Keeping the commitments in the envelope means a block builder can read the blob count and per-blob fee directly from the transaction header.

EVM-side, blobs are already accessible: the `BLOBHASH` opcode exposes the versioned hashes to contract code. Rollup posters and DA users see the same EVM-level interface as in EIP-4844 today.

### No authorization list

This EIP does not introduce its own authorization-list mechanism for installing EIP-7702 delegations. Two reasons:

1. **EIP-7702 already provides one.** An EOA opts into delegation via a separate EIP-7702 transaction (or, post-fork, via a `SETDELEGATE` operation inside a `deploy` frame). Once the delegation is installed, frame transactions see it natively via the existing EIP-7702 delegated-code rules; see [EIP-7702 integration](#eip-7702-integration).
2. **Authorization lists assume ECDSA.** EIP-7702's authorization list is bound to secp256k1 signatures via `ecrecover` over the authority's address. Replicating that mechanism inside this EIP would lock the post-quantum migration path that frame transactions are otherwise designed to keep open. By treating delegation installation as a one-time setup external to the frame-transaction envelope, the per-transaction signature scheme remains free to evolve.

### No access list

The access list was introduced to address a particular backwards compatibility issue that was caused by EIP-2929. The risk-reward of using an access list successfully is high. A single miss, paying to warm a storage slot that does not end up getting used, causes the overall transaction cost to be greater than had it not been included at all.

Future optimizations based on pre-announcing state elements a transaction will touch will be covered by block level access lists.

### Atomic batching

Atomic batching allows multiple frames to be grouped into a single all-or-nothing unit. This is useful when a sequence of calls is only meaningful if all succeed together, such as an approval followed by a swap, or a series of interdependent state changes. Without this feature, a revert in one frame would leave the preceding frames' state changes applied, potentially leaving the account in an undesirable intermediate state.

Using a flag to indicate atomic batches saves us from having to introduce a new mode. Batches are identified purely by consecutive frames with the flag set, terminated by a frame without it. This design enables consecutive atomic batches since the batch boundary is clearly indicated by the frame without the flag.

### Per-frame cost

Each frame incurs a fixed CALL execution-context overhead (100) plus `G_log` (375) for the receipt sub-entry it produces, giving `FRAME_TX_PER_FRAME_COST = 475`. The execution-context component covers context setup, mode dispatch, and gas accounting at the frame boundary, analogous to the fixed overhead of a CALL. The `G_log` component covers the `[status, gas_used, logs]` receipt sub-entry that each frame adds to the transaction receipt, which must be serialized, hashed into the receipt trie, and proven by ZK-EVM implementations. Cold/warm access costs for the frame's target account are charged within the frame's own `gas_limit` through the normal EVM warm/cold accounting, not through the per-frame cost.

### Per-frame value

A design goal of the frame transaction is to provide a good experience out-of-the-box for users and to reduce the threat surface of smart contract wallets. Like batching, sending native value is a part of achieving that.

Restricting non-zero `value` to `SENDER` frames keeps `VERIFY` and `DEFAULT` frames side-effect-free with respect to ETH transfer semantics, preserves the intended `STATICCALL`-like behavior of `VERIFY`, and avoids requiring the protocol-defined `ENTRY_POINT` caller to fund top-level ETH transfers.

### Externally Owned Account (EOA) support

While we expect EOA users to migrate to smart accounts eventually, we recognize that most Ethereum users today are using EOAs, so we want to improve UX for them where we can.

Thanks to the default code, EOAs today can use frame transactions to reap many benefits of account abstraction, including sending sponsored transactions, paying gas in ERC-20 tokens, batch transactions, and more.

### Non-canonical paymasters in the mempool

The primary use case for non-canonical paymasters is to enable users to pay gas with a dedicated "gas account," so that their other accounts can transact without holding any ETH. For example, a user might have a single account that holds some ETH, while other accounts only hold stablecoins and NFTs, and they can transact freely with these other accounts while using the gas account as the paymaster.

Note that users can use any EOA as a paymaster thanks to the [default code](#default-code).

### Examples

#### Example 1: Simple Transaction (EOA)

| Frame | Caller      | Target        | Value | Flags                         | Data            | Mode   |
| ----- | ----------- | ------------- | ----- | ----------------------------- | --------------- | ------ |
| 0     | ENTRY_POINT | Null (sender) | 0     | APPROVE_EXECUTION_AND_PAYMENT | Signature       | VERIFY |
| 1     | Sender      | Target        | 0     | APPROVE_SCOPE_NONE            | Call data       | SENDER |

Frame 0 runs the [default code](#default-code) because `tx.sender` is an EOA with no installed code. The default code recovers the sender from the signature using `keccak256(compute_sig_hash(tx) || state[tx.sender].nonce)`, increments `state[tx.sender].nonce` as an approval effect, and calls `APPROVE(APPROVE_EXECUTION_AND_PAYMENT)`. Frame 1 executes and exits normally via `RETURN`.

The mempool processes this as the recognized prefix `[self_verify]`, with replay protection satisfied via condition (1) of [Replay Protection in the Public Mempool](#replay-protection-in-the-public-mempool).

#### Example 1a: Simple ETH transfer (EOA)

| Frame | Caller      | Target        | Value  | Flags                         | Data       | Mode   |
| ----- | ----------- | ------------- | ------ | ----------------------------- | ---------- | ------ |
| 0     | ENTRY_POINT | Null (sender) | 0      | APPROVE_EXECUTION_AND_PAYMENT | Signature  | VERIFY |
| 1     | Sender      | Destination   | Amount | APPROVE_SCOPE_NONE            | Empty      | SENDER |

A simple transfer: target the `SENDER` frame at the destination, set `value` to the transfer amount.

#### Example 1b: First-time smart account deployment

| Frame | Caller      | Target        | Value  | Flags                         | Data           | Mode    |
| ----- | ----------- | ------------- | ------ | ----------------------------- | -------------- | ------- |
| 0     | ENTRY_POINT | Deployer      | 0      | APPROVE_SCOPE_NONE            | Initcode, Salt | DEFAULT |
| 1     | ENTRY_POINT | Null (sender) | 0      | APPROVE_EXECUTION_AND_PAYMENT | Sig + nonce    | VERIFY  |
| 2     | Sender      | Destination   | Amount | APPROVE_SCOPE_NONE            | Empty          | SENDER  |

The deploy frame runs first (since `tx.sender` needs code in order to validate the transaction). After deployment, frame 1 runs the now-installed smart-account code, which reads its own storage slot to check the claimed nonce, increments it as an approval effect, and `APPROVE`s.

The deploy frame would typically call the [EIP-7997](./eip-7997.md) deterministic factory predeploy. Since `tx.sender` is not authenticated at this point, the user must choose an initcode that is safe to deploy by anyone.

#### Example 1c: Expiring transaction

| Frame | Caller      | Target          | Value | Flags                         | Data       | Mode   |
| ----- | ----------- | --------------- | ----- | ----------------------------- | ---------- | ------ |
| 0     | ENTRY_POINT | ExpiryVerifier* | 0     | APPROVE_SCOPE_NONE            | Deadline   | VERIFY |
| 1     | ENTRY_POINT | Null (sender)   | 0     | APPROVE_EXECUTION_AND_PAYMENT | Signature  | VERIFY |
| 2     | Sender      | Target          | 0     | APPROVE_SCOPE_NONE            | Call data  | SENDER |

`ExpiryVerifier*` denotes any contract whose runtime code matches the canonical `ExpiryVerifier` pattern. The mempool drops this transaction once `Deadline < block.timestamp`. For pattern-matching purposes the expiry frame is skipped, so the recognized prefix is `[self_verify]`.

#### Example 2: Atomic Approve + Swap

| Frame | Caller      | Target        | Value | Flags                         | Data                 | Mode   |
| ----- | ----------- | ------------- | ----- | ----------------------------- | -------------------- | ------ |
| 0     | ENTRY_POINT | Null (sender) | 0     | APPROVE_EXECUTION_AND_PAYMENT | Signature            | VERIFY |
| 1     | Sender      | ERC-20        | 0     | ATOMIC_BATCH_FLAG             | approve(DEX, amount) | SENDER |
| 2     | Sender      | DEX           | 0     | APPROVE_SCOPE_NONE            | swap(...)            | SENDER |

Frame 0 verifies the signature, bumps `state[sender].nonce` as an approval effect, and calls `APPROVE(APPROVE_EXECUTION_AND_PAYMENT)`. Frames 1 and 2 form an atomic batch: if the swap in frame 2 reverts, the ERC-20 approval from frame 1 is also reverted. The nonce bump committed in frame 0 is NOT reverted by the atomic-batch rollback, since it is an approval effect.

#### Example 3: Sponsored Transaction (Fee Payment in ERC-20)

| Frame | Caller      | Target        | Value | Flags              | Data                   | Mode    |
| ----- | ----------- | ------------- | ----- | ------------------ | ---------------------- | ------- |
| 0     | ENTRY_POINT | Null (sender) | 0     | APPROVE_EXECUTION  | Signature              | VERIFY  |
| 1     | ENTRY_POINT | Sponsor       | 0     | APPROVE_PAYMENT    | Sponsor data           | VERIFY  |
| 2     | Sender      | ERC-20        | 0     | APPROVE_SCOPE_NONE | transfer(Sponsor,fees) | SENDER  |
| 3     | Sender      | Target addr   | 0     | APPROVE_SCOPE_NONE | Call data              | SENDER  |
| 4     | ENTRY_POINT | Sponsor       | 0     | APPROVE_SCOPE_NONE | Post op call           | DEFAULT |

- Frame 0: Verifies signature, bumps account nonce, calls `APPROVE(APPROVE_EXECUTION)`.
- Frame 1: Checks that the user has enough ERC-20 tokens and that the next `SENDER` frame is an ERC-20 send of the right size to the sponsor. Calls `APPROVE(APPROVE_PAYMENT)`.
- Frame 2: Sends tokens to sponsor.
- Frame 3: User's intended call.
- Frame 4 (optional): Check unpaid gas, refund tokens, possibly convert tokens to ETH on an AMM.

#### Example 4: Keyed-nonce privacy protocol (smart-contract shared sender)

| Frame | Caller      | Target          | Value | Flags                         | Data                          | Mode   |
| ----- | ----------- | --------------- | ----- | ----------------------------- | ----------------------------- | ------ |
| 0     | ENTRY_POINT | Shared sender   | 0     | APPROVE_EXECUTION_AND_PAYMENT | (nullifier, 0, ZK proof)      | VERIFY |
| 1     | Sender      | Recipient       | Amount| APPROVE_SCOPE_NONE            | Empty                         | SENDER |

A privacy protocol routes many users through a single shared smart-contract `sender`. The verifier frame's data carries `(nullifier, 0, proof)`. The sender's contract code:

```solidity
function verify(bytes calldata data) external {
    (bytes32 nullifier, uint64 seq, bytes memory proof) = abi.decode(data, (bytes32, uint64, bytes));
    require(seq == 0 && keyedNonces[uint256(nullifier)] == 0, "nullifier consumed");
    keyedNonces[uint256(nullifier)] = 1;          // approval effect (SSTORE to own storage)
    require(verifyProof(proof, nullifier, TXPARAM(SIG_HASH)));
    APPROVE(APPROVE_EXECUTION_AND_PAYMENT);
}
```

The `SSTORE` lands in the shared sender's own storage and is journaled as an approval effect: the nullifier is consumed atomically with payment approval and cannot be un-burned by a later revert. Different users on different nullifiers do not block each other; the mempool admits concurrent pending transactions on distinct keys subject to its own dependency tracking on the affected slots.

No protocol-level keyed-nonce machinery is involved. The contract owns the storage layout, the slot derivation, the data format, and the signature scheme.

#### Example 5: EIP-1559 transaction expressed as frames

This shows how a current-day EIP-1559 transaction maps to the frame transaction model. A legacy EIP-1559 transaction has fields `(chain_id, nonce, max_priority_fee_per_gas, max_fee_per_gas, gas_limit, to, value, data, access_list, v, r, s)`. As frames, from an EOA:

| Frame | Caller      | Target        | Value | Flags                         | Data         | Mode   |
| ----- | ----------- | ------------- | ----- | ----------------------------- | ------------ | ------ |
| 0     | ENTRY_POINT | Null (sender) | 0     | APPROVE_EXECUTION_AND_PAYMENT | Signature    | VERIFY |
| 1     | Sender      | `to`          | value | APPROVE_SCOPE_NONE            | `data`       | SENDER |

Mapping the legacy fields:

- `chain_id` → envelope `chain_id`
- `nonce` → no longer in envelope; default code reads `state[tx.sender].nonce` and commits to it via signature
- `max_priority_fee_per_gas`, `max_fee_per_gas` → envelope (same names)
- `gas_limit` → frame 1's `gas_limit`, plus `FRAME_TX_INTRINSIC_COST` + per-frame overhead for frame 0
- `to`, `value`, `data` → frame 1's `target`, `value`, `data`
- `access_list` → dropped (see [No access list](#no-access-list))
- `(v, r, s)` → frame 0's `data` (the signature, elided in `compute_sig_hash`)

The default code's augmented signature hash `keccak256(compute_sig_hash(tx) || state[sender].nonce)` reproduces the replay-protection semantics of legacy nonces. A user moving from an EIP-1559 wallet to a frame-transaction wallet keeps the same account, the same key, and the same sequence space; their wallet just emits frame transactions instead of EIP-1559 transactions.

For a contract call (`to` is non-zero), `data` carries the calldata. For a deployment (`to == None`), it would target a deployer factory in `SENDER` mode (frame transactions do not provide a built-in "to == None creates" shortcut; deployment is just a `SENDER` frame calling a factory).

#### Example 6: EIP-4844 blob transaction expressed as frames

An EIP-4844 blob-carrying transaction has the additional fields `(max_fee_per_blob_gas, blob_versioned_hashes)`. These remain in the envelope (see [Why blobs stay in the envelope](#why-blobs-stay-in-the-envelope)). The frame layout is unchanged from Example 5:

| Frame | Caller      | Target          | Value | Flags                         | Data       | Mode   |
| ----- | ----------- | --------------- | ----- | ----------------------------- | ---------- | ------ |
| 0     | ENTRY_POINT | Null (sender)   | 0     | APPROVE_EXECUTION_AND_PAYMENT | Signature  | VERIFY |
| 1     | Sender      | Rollup contract | 0     | APPROVE_SCOPE_NONE            | Commitment | SENDER |

The envelope carries the blob fee and blob hashes; frame 1's contract reads the hashes via `BLOBHASH` exactly as a current EIP-4844 transaction would. The signature in frame 0 commits to the entire envelope (via `compute_sig_hash`), so the blob commitments are authenticated by the same signature that authenticates the rest of the transaction. Blob fee accounting (`blob_fees = len(blob_versioned_hashes) * GAS_PER_BLOB * blob_base_fee`) is performed identically to EIP-4844.

A rollup posting an L2 batch in frame-transaction form looks just like the legacy EIP-4844 path: same gas economics, same blob lifecycle, same `BLOBHASH` access in the EVM. The execution-layer abstraction added by this EIP does not interact with the data-availability layer.

#### Example 7: EIP-7702-delegated EOA with keyed nonces in EOA storage

This is the case where this EIP and EIP-7702 compose cleanly. Alice's EOA installs an EIP-7702 delegation indicator (via a separate one-time EIP-7702 transaction) pointing to a canonical smart-account template. Once installed, Alice's EOA has effective code and effective storage; her frame transactions look like a smart-account transaction:

| Frame | Caller      | Target           | Value | Flags                         | Data                  | Mode   |
| ----- | ----------- | ---------------- | ----- | ----------------------------- | --------------------- | ------ |
| 0     | ENTRY_POINT | Alice (delegated)| 0     | APPROVE_EXECUTION_AND_PAYMENT | (key, seq, signature) | VERIFY |
| 1     | Sender      | Target           | 0     | APPROVE_SCOPE_NONE            | Call data             | SENDER |

The delegated code (running under Alice's `ADDRESS`) implements its own replay protection:

```solidity
mapping(uint256 => uint64) keyedNonces;  // stored at Alice's address

function verify(bytes calldata data) external {
    (uint256 key, uint64 seq, bytes memory sig) = abi.decode(data, (uint256, uint64, bytes));
    require(seq == keyedNonces[key]);
    keyedNonces[key] = seq + 1;                   // approval effect at state[Alice]
    bytes32 h = keccak256(abi.encode(TXPARAM(SIG_HASH), key, seq));
    require(ecrecover(h, sig) == owner);
    APPROVE(APPROVE_EXECUTION_AND_PAYMENT);
}
```

Alice now has multi-dimensional nonces at her EOA address without any protocol changes beyond the two primitives in [Minimal protocol surface](#minimal-protocol-surface). She can have many concurrent transactions in flight on different keys; she can rotate the underlying signing key by changing `owner`; she can later migrate to a post-quantum scheme by re-delegating; her EOA address never changes.

The mempool admits this transaction because the delegated code matches a recognized smart-account template (condition (2) of [Replay Protection in the Public Mempool](#replay-protection-in-the-public-mempool)). EOAs that delegate to bespoke contracts go through builders.

This is +5 bytes over a stripped EIP-1559 ETH transfer (the chief overhead being `sender` as an explicit envelope field), in exchange for the full frame-transaction abstraction. ## Backwards Compatibility

The `ORIGIN` opcode behavior changes for frame transactions, returning the frame's caller rather than the traditional transaction origin. This is consistent with the precedent set by EIP-7702, which already modified `ORIGIN` semantics. Contracts that rely on `ORIGIN = CALLER` for security checks (a discouraged pattern) may behave differently under frame transactions.

## Security Considerations

### Transaction Propagation

Frame transactions introduce new denial-of-service vectors for transaction pools that node operators must mitigate. Because validation logic is arbitrary EVM code, attackers can craft transactions that appear valid during initial validation but become invalid later. Without any additional policies, an attacker could submit many transactions whose validity depends on some shared state, then submit one transaction that modifies that state, and cause all other transactions to become invalid simultaneously. This wastes the computational resources nodes spent validating and storing these transactions.

#### Example Attack

A simple example is transactions that check `block.timestamp`:

```solidity
function validateTransaction() external {
    require(block.timestamp < SOME_DEADLINE, "expired");
    // ... rest of validation
    APPROVE(APPROVE_EXECUTION_AND_PAYMENT);
}
```

Such transactions are valid when submitted but become invalid once the deadline passes, without any on-chain action required from the attacker.

#### Deploy Frame Front-Running

If a transaction uses a `deploy` frame, that frame executes before the sender is authenticated. An observer can front-run the same deterministic deployment and cause the `deploy` frame to fail because code is already present at `tx.sender`. Accordingly, the deploy frame's calldata (and any initcode it carries) must be safe to submit by any party, and wallets should expect resubmission without the `deploy` frame once deployment has already occurred.

#### Explicit Sender State-Read Amplification

Because `tx.sender` is explicit in the transaction envelope, an attacker can submit many invalid frame transactions that name arbitrary sender addresses and force nodes to read sender state and sender storage during validation simulation. Public mempool implementations should therefore perform all available structural and stateless checks (frame layout, recognized prefix shape, recognized verifier template) before any storage access, and should consider peer-level rate limiting or other DoS mitigations for repeated invalid transactions that vary `tx.sender`.

#### Contract-Managed Replay Protection

The execution layer does not enforce replay protection; the verifier code in the validation prefix does. A buggy verifier that fails to record per-transaction state in `tx.sender`'s storage (or, for EOAs, fails to use the default code that bumps `state[tx.sender].nonce`) can enable infinite replay of the same signed transaction. This is a contract-correctness concern of the same nature as any other contract bug.

The public mempool restricts propagation to transactions whose verifier code it recognizes (see [Replay Protection in the Public Mempool](#replay-protection-in-the-public-mempool)), which is the primary defense against accidentally-vulnerable verifiers reaching wide propagation. Builders accepting transactions outside this rule take on a "you are trusting this verifier" assumption explicitly.

Verifier authors implementing keyed nonces, nullifier tables, or other application-defined replay schemes SHOULD:

- Bind the application state to the canonical signature hash via `keccak256(TXPARAM(SIG_HASH) || application_state)` or equivalent. Treating `application_state` as authorization without committing to it via signature is unsafe.
- Domain-separate any input derived from a per-use identifier (e.g., nullifiers) and reject derived keys that would collide with reserved values.
- Choose storage layouts that avoid clashing with other application state in the same contract.

A keyed-nonce frame transaction from a smart account does not advance `state[tx.sender].nonce`. If such a transaction executes `CREATE` at `tx.sender`, the created address depends on the legacy account nonce at execution time, which an attacker can manipulate via concurrent transactions of other types. Applications whose semantics depend on a `CREATE` address SHOULD use `CREATE2` or MUST authenticate the expected pre-state legacy nonce by reading it during validation.

A "send another transaction with the same legacy nonce" cancellation strategy does not invalidate a pending smart-account frame transaction that uses keyed nonces. Replacement requires another transaction that intentionally consumes the same keyed slot, subject to the mempool's replacement rules.

#### Persistence of Approval Effects

Approval effects — the `APPROVE` instruction's updates to `payer`/`sender_approved`, and the `SSTORE`s a verifier frame performs to its own storage — persist through later-frame reverts and `SENDER` atomic-batch rollback. Applications that rely on observable post-approval state SHOULD minimize post-approval revert paths; in particular, single-use-key applications cannot "unburn" a key by reverting a later frame.

A consumed slot in a verifier's keyed-nonce or nullifier table occupies one persistent storage entry priced by ordinary `SSTORE` rules. State growth is therefore bounded by the block gas limit divided by the `SSTORE` fresh-slot cost (~20,000 gas), before accounting for other transaction costs.

#### Cross-frame Data Visibility During Validation

`FRAMEPARAM`, `FRAMEDATALOAD`, and `FRAMEDATACOPY` allow validation code to inspect other frames, including later `SENDER` frames and their `value`s. As a result, paymasters and other `VERIFY` frames can observe user operation parameters before approval and may condition their behavior on that information. Users should therefore treat non-`VERIFY` frame parameters and data as visible to validation logic and should not rely on untrusted paymasters or verifiers to keep such information private.

##### Mitigations

Node implementations should consider restricting which opcodes and storage slots validation frames can access, similar to ERC-7562. This isolates transactions from each other and limits mass invalidation vectors.

It's recommended that to *validate* the transaction, a specific frame structure is enforced and the amount of gas that is expended executing the validation phase must be limited. Once the validation prefix reaches payer approval via `APPROVE(APPROVE_PAYMENT)` or `APPROVE(APPROVE_EXECUTION_AND_PAYMENT)`, the transaction can be included in the mempool and propagated to peers safely.

For deployment of the sender account in the first frame, the mempool enforces deploy-frame determinism via the validation trace rules. Any contract may be used as `frame.target`, provided the frame's execution satisfies those rules — notably, it must not read mutable state outside `tx.sender` or maintain per-deploy factory storage (counters, reentrancy flags, etc.), so that the deployment result is independent of chain state. Factories deployed via the [EIP-7997](./eip-7997.md) deterministic factory predeploy are the canonical choice for acquiring a cross-chain-stable factory address.

In general, it can be assumed that handling of frame transactions imposes similar restrictions as EIP-7702 on mempool relay, i.e. only a single transaction can be pending for an account that uses frame transactions.
