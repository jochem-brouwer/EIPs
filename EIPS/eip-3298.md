## Abstract

This EIP removes the storage-clearing refund (`STORAGE_CLEAR_REFUND`, as defined by [EIP-8038](./eip-8038.md)) and the transaction-level refund cap, which was lowered by [EIP-3529](./eip-3529.md). The only refund that remains is [EIP-8038](./eip-8038.md)'s net-metered `STORAGE_WRITE` reversal, which returns gas charged earlier in the same transaction when a storage slot is restored to its transaction-start value. Because that reversal can never exceed the charges it undoes and the the refund is applied to the state reservoir per [EIP-8037](./eip-8037.md) self-bounded and the cap is no longer needed.

## Motivation

Refunds were originally introduced to incentivize "good state hygiene": clearing storage slots and contracts that are no longer needed. This incentive has not worked in practice, and the current answer to battle state growth is repricing state creation ([EIP-8037](./eip-8037.md)), not per-slot cleanup rebates.

What refunds cost the protocol today is complexity in the end-of-transaction gas settlement:

* The refund counter must be capped at 20% of gas used ([EIP-3529](./eip-3529.md), see `MAX_REFUND_QUOTIENT`), and this cap interacts non-obviously with the calldata floor of [EIP-7623](./eip-7623.md) / [EIP-7976](./eip-7976.md): the floor is applied after refunds, so a refund can be partially or fully negated by the floor. Whether the cap applies to execution gas, state gas, or their sum requires careful specification under [EIP-8037](./eip-8037.md)'s two-dimensional metering.
* The clearing refund moves gas value across transactions: gas charged for a `GAS_STORAGE_SET` in one transaction is partially rebated by a clear in a later transaction. This is the mechanism GasToken abused before [EIP-3529](./eip-3529.md), and while it is no longer economically exploitable that EIP and under [EIP-8037](./eip-8037.md) pricing (a new slot costs `STATE_BYTES_PER_STORAGE_SET × CPSB` in state gas while the clear refunds far less), it still requires every client and every gas estimator to model a cross-transaction subsidy that no longer serves a purpose. Per block accounting, the refunds are already removed per [EIP-7778](./eip-7778.md)

By the fork this EIP targets, the other historical refunds are already gone:

* The `SELFDESTRUCT` refund was removed by [EIP-3529](./eip-3529.md).
* The [EIP-7702](./eip-7702.md) per-authorization refund (`PER_EMPTY_ACCOUNT_COST - PER_AUTH_BASE_COST` for pre-existing authorities) is removed by [EIP-2780](./eip-2780.md) (Glamsterdam), which replaces the charge-then-refund pattern with conditional runtime charges.
* Block-level gas accounting already excludes refunds entirely, per [EIP-7778](./eip-7778.md) (Glamsterdam).

This leaves `SSTORE` as the only source of refunds. Of its refund rules, the write reversal is genuine net metering — a slot that ends the transaction at its starting value should pay only access costs — while the clearing refund is a cross-transaction incentive with no remaining justification. This EIP removes the latter and keeps the former, and, since the former is bounded by charges made in the same transaction, removes the refund cap as well.

## Specification

This EIP is specified as a delta against [EIP-8037](./eip-8037.md) and [EIP-8038](./eip-8038.md) and assumes both are active, together with [EIP-2780](./eip-2780.md) and [EIP-7778](./eip-7778.md).

### Parameters removed

| Parameter | Previous value | Source |
| :---: | :---: | :---: |
| `STORAGE_CLEAR_REFUND` | 11,616 | [EIP-8038](./eip-8038.md) |

`STORAGE_CLEAR_REFUND` (the successor of [EIP-3529](./eip-3529.md)'s `SSTORE_CLEARS_SCHEDULE`) is removed from the gas schedule.

### `SSTORE` refund rules

The three refund rules of [EIP-8038](./eip-8038.md) are replaced by a single rule, evaluated on every `SSTORE`. As in [EIP-2200](./eip-2200.md), the *original value* is the slot's value at the start of the current transaction and the *current value* is its value just before the `SSTORE` executes:

1. `STORAGE_WRITE` is refunded if the new value equals the original value and differs from the current value (a change made earlier in the same transaction is undone, restoring the slot's transaction-start value).

[EIP-8038](./eip-8038.md)'s rule 1 (`STORAGE_CLEAR_REFUND` added when a slot with a non-zero original value is cleared) and rule 2 (`STORAGE_CLEAR_REFUND` subtracted when such a cleared slot is restored) are removed. Rule 2 existed only to reverse rule 1 and is meaningless without it.

The `SSTORE` charging rules (access, write, and state-creation components) and the state-gas charges and refills of [EIP-8037](./eip-8037.md) are unchanged. State-gas refills are not refunds and do not enter the refund counter.

The complete `SSTORE` case table, superseding the corresponding table in [EIP-8038](./eip-8038.md):

| Original value | Current value | New value | Access status | Description | Regular-gas charges/refunds | State-gas charges/refills |
| :---: | :---: | :---: | :---: | :---: | :---: | :---: |
| 0 | 0 | x | Cold | New slot | `COLD_STORAGE_ACCESS` + `STORAGE_WRITE` charged | `GAS_STORAGE_SET` charged |
| 0 | 0 | x | Warm | New slot | `WARM_ACCESS` + `STORAGE_WRITE` charged | `GAS_STORAGE_SET` charged |
| x | x | y | Cold | Existing slot, first change | `COLD_STORAGE_ACCESS` + `STORAGE_WRITE` charged | no state-gas adjustments |
| x | x | y | Warm | Existing slot, first change | `WARM_ACCESS` + `STORAGE_WRITE` charged | no state-gas adjustments |
| x | x | 0 | Cold | Cleared slot, non-zero at transaction start | `COLD_STORAGE_ACCESS` + `STORAGE_WRITE` charged | no state-gas adjustments |
| x | x | 0 | Warm | Cleared slot, non-zero at transaction start | `WARM_ACCESS` + `STORAGE_WRITE` charged | no state-gas adjustments |
| 0 | x | 0 | Warm | Set slot reset to zero (zero at transaction start) | `WARM_ACCESS` charged, `STORAGE_WRITE` refunded | `GAS_STORAGE_SET` refilled |
| 0 | x | y | Warm | Slot set earlier in the transaction written to a different non-zero value | `WARM_ACCESS` charged | no state-gas adjustments |
| x | y | x | Warm | Previously-modified slot reset to original value | `WARM_ACCESS` charged, `STORAGE_WRITE` refunded | no state-gas adjustments |
| x | y | 0 | Warm | Previously-modified slot cleared, non-zero at transaction start | `WARM_ACCESS` charged | no state-gas adjustments |
| x | 0 | x | Warm | Cleared slot restored to original value | `WARM_ACCESS` charged, `STORAGE_WRITE` refunded | no state-gas adjustments |
| x | 0 | y | Warm | Cleared slot written to a new non-zero value | `WARM_ACCESS` charged | no state-gas adjustments |
| x | y | z | Warm | Previously-modified slot written to another non-zero value | `WARM_ACCESS` charged | no state-gas adjustments |

### Removal of the refund cap

The transaction gas settlement of [EIP-8037](./eip-8037.md) is updated to remove the [EIP-3529](./eip-3529.md) cap:

```python
tx_gas_used_before_refund = tx.gas - tx_output.gas_left - tx_output.state_gas_reservoir
tx_gas_used_after_refund = tx_gas_used_before_refund - tx_output.refund_counter
tx_gas_used = max(tx_gas_used_after_refund, calldata_floor_gas_cost)
```

That is, `tx_gas_refund = min(tx_gas_used_before_refund // 5, tx_output.refund_counter)` becomes simply `tx_output.refund_counter`. The [EIP-7623](./eip-7623.md) calldata floor continues to apply after refunds, and the receipt `cumulative_gas_used` continues to use the post-floor value.

Block-level gas accounting is unchanged: per [EIP-7778](./eip-7778.md) and [EIP-8037](./eip-8037.md), the execution-gas dimension counts `max(tx_gas_used_before_refund - tx_state_gas, calldata_floor_gas_cost)`, before refunds.

## Rationale

### Why keep the write reversal

The `STORAGE_WRITE` refund is not an incentive; it is the accounting rule that makes `SSTORE` net-metered within a transaction. A slot that ends the transaction at its starting value has consumed no durable write, so it should pay only its access costs; without the reversal, a round trip such as `x → y → x` would pay `STORAGE_WRITE` for a write that was undone. Removing it would overcharge common patterns (transient locks and re-entrancy guards on pre-[EIP-1153](./eip-1153.md) contracts, netting in settlement systems) without simplifying anything: clients must track the original value regardless, because the charging rules depend on it.

Crucially, the write reversal cannot move gas across transactions: every refund it grants reverses a `STORAGE_WRITE` charge made earlier in the same transaction. It therefore has none of the properties that motivated removing refunds in the first place.

### Why the cap can be removed

With the clearing refund gone, the refund counter satisfies the invariant that it never exceeds the sum of `STORAGE_WRITE` charges already paid in the same transaction: a slot can only be restored to its original value (triggering the refund) after a write moved it away from that value (triggering the charge), and each restore reverses exactly one such charge. Consequently `tx_gas_used_after_refund` is always at least the transaction's non-`STORAGE_WRITE` costs and can never approach zero, let alone go negative.

The [EIP-3529](./eip-3529.md) cap existed to bound the block-size impact of refunds and to limit gas banking. The first concern is fully addressed by [EIP-7778](./eip-7778.md), which counts pre-refund gas at the block level; the second is impossible for a same-transaction reversal. Keeping the cap would only preserve the specification complexity this EIP sets out to remove, including the question of how the cap composes with the calldata floor and with two-dimensional metering.

### Why remove the clearing refund

The clearing refund is the last remaining cross-transaction refund. Its original purpose — incentivizing state cleanup — is obsolete: state growth is now priced directly at creation time by [EIP-8037](./eip-8037.md), and under that pricing the refund is far too small relative to `STATE_BYTES_PER_STORAGE_SET × CPSB` to function as an incentive or as a gas-banking vehicle. What remains is pure specification and implementation burden: an extra parameter, two refund rules (the grant and its reversal), and the refund cap that exists chiefly to contain it.

Note that [EIP-8038](./eip-8038.md) raises `STORAGE_CLEAR_REFUND` to 11,616 in Glamsterdam; this EIP, scheduled for the following fork, removes the parameter entirely.

### Refunds already removed elsewhere

This EIP deliberately does not respecify the `SELFDESTRUCT` refund (removed by [EIP-3529](./eip-3529.md)) or the [EIP-7702](./eip-7702.md) per-authorization refund (removed by [EIP-2780](./eip-2780.md), which charges the state-dependent authorization costs conditionally at runtime instead of charging worst-case and refunding). After this EIP, the `STORAGE_WRITE` reversal is the only refund in the protocol, and the refund counter is a plain, uncapped accumulator of same-transaction reversals.

### Relation to the original version of this EIP

The original (2021) version of this EIP removed all refunds, including the reset-to-original accounting, on the grounds that partial retention was not worth the complexity. The gas model has since changed around it: [EIP-3529](./eip-3529.md) removed the `SELFDESTRUCT` refund and capped the rest, [EIP-7778](./eip-7778.md) removed refunds from block accounting, [EIP-2780](./eip-2780.md) removed the [EIP-7702](./eip-7702.md) refund, and [EIP-8038](./eip-8038.md) restructured `SSTORE` into explicit access/write components whose net metering *is* the reset refund. In that model, the write reversal carries the accounting semantics while the clearing refund carries all the residual complexity, so the line is drawn between them.

## Backwards Compatibility

This is a backwards-incompatible gas repricing that requires a scheduled network upgrade.

Refunds are applied only in the end-of-transaction settlement, so they cannot affect how much gas is available to any call frame during execution. Removing the clearing refund therefore cannot break contract execution, but it changes the net cost of transactions that clear storage: a transaction that clears a slot whose original value is non-zero no longer receives 11,616 gas back per cleared slot. Applications that batch storage cleanup for the refund will see proportionally higher net costs.

Gas estimators and wallets MUST remove the clearing-refund and refund-cap logic from `eth_estimateGas` and fee computation.

## Test Cases

The following sequences (single warm slot, values symbolic) illustrate the refund counter under this EIP. `W` denotes `STORAGE_WRITE`, refunds are shown as negative:

| Sequence (original value first) | Charges | Refund counter | Net write cost |
| :--- | :--- | :---: | :---: |
| `0 → x` | `W` | 0 | `W` |
| `0 → x → 0` | `W` | `W` | 0 |
| `x → 0` | `W` | 0 | `W` |
| `x → 0 → x` | `W` | `W` | 0 |
| `x → y → x` | `W` | `W` | 0 |
| `x → y → 0` | `W` | 0 | `W` |
| `x → y → x → z` | `W`, `W` | `W` | `W` |
| `x → 0 → x → 0` | `W`, `W` | `W` | `W` |

In every case the refund counter is bounded by the `STORAGE_WRITE` charges of the same transaction, and no refund cap is applied. State-gas charges and refills ([EIP-8037](./eip-8037.md)) are orthogonal and unchanged.

Tests should additionally cover:

* A transaction clearing many slots, verifying no refund is granted and `tx_gas_used` equals pre-refund gas (modulo the calldata floor).
* A transaction whose refund counter exceeds 20% of gas used before refunds (impossible to construct with clearing refunds removed only via reversals of same-transaction charges; the test asserts the uncapped subtraction is applied).
* Interaction with the [EIP-7623](./eip-7623.md) floor: a refund-carrying transaction whose `tx_gas_used_after_refund` falls below `calldata_floor_gas_cost`, verifying the floor binds.
* Block accounting per [EIP-7778](./eip-7778.md): refunds reduce the sender's payment but not the block's execution-gas usage.

## Security Considerations

Removing the refund cap is safe only because the remaining refund is self-bounded; this invariant is load-bearing. Any future EIP that adds a refund not backed by a same-transaction charge MUST either reintroduce a cap or demonstrate an equivalent bound, otherwise a transaction could pay less than the resources it consumed.

Since [EIP-7778](./eip-7778.md) already excludes refunds from block-level accounting, this EIP does not change worst-case block resource consumption; it only increases the net payment of storage-clearing transactions.
